# 向量数据库选型说明

## 1. 文档目的

本文件用于说明“基于 RAG 的编程技术文档问答助手”项目中是否需要向量数据库、应在什么阶段引入向量检索能力，以及当前项目更适合采用哪一种技术方案。

## 2. 是否需要向量数据库

结论：

本项目最终建议具备向量检索能力，当前阶段优先采用 PostgreSQL + pgvector 方案，不强制接入独立向量数据库或独立检索引擎。

原因如下：

1. 如果系统只做关键词检索，能够完成基础问答演示，但对同义表达、概念类问题、术语变形问题的召回效果有限。
2. 本项目知识来源以官方技术文档为主，文档表述通常较规范，而用户问题往往更口语化，语义检索能明显提升召回质量。
3. RAG 问答效果高度依赖召回质量，如果没有向量检索，系统更容易出现“检索不到”或“上下文不够相关”的问题。

因此，本项目应采用“分阶段建设”策略：

- 第一阶段：先完成文档入库、切片、PostgreSQL 存储、基础全文检索
- 第二阶段：增加向量化、pgvector 语义检索与混合检索能力
- 第三阶段：实现重排、召回评估与持续优化，必要时再评估独立检索引擎

## 3. 为什么不能只靠关键词检索

关键词检索适合以下场景：

- 用户问题中包含明确技术名词
- 文档与问题表述高度一致
- 问题偏向术语查询、命令查询、配置项查询

但在以下场景中效果较弱：

- 用户使用近义表达提问
- 用户提问较口语化，不包含文档中的关键术语
- 用户提问是原理类问题，需要理解语义而不是匹配关键词

示例：

- 用户问题：Spring Boot 为什么会自动帮我创建很多 Bean？
- 文档描述：Auto-configuration、Conditional Configuration、Starter、Bean Registration

此时如果只做关键词匹配，可能无法稳定命中；如果引入向量检索，则更容易召回与“自动配置原理”相关的知识片段。

## 4. 方案选择原则

本项目的检索方案需要满足以下要求：

1. 支持技术文档的全文检索。
2. 支持知识片段向量检索。
3. 支持关键词检索与语义检索结合。
4. 支持后续扩展重排、过滤、标签检索等能力。
5. 尽量降低毕业设计项目的开发和部署复杂度。

## 5. 可选方案对比

### 5.1 PostgreSQL + pgvector

优点：

- 一套系统同时承担业务数据存储、基础全文检索和向量检索
- 部署和运维成本低于 MySQL + Elasticsearch 双系统方案
- 数据一致性更容易保证，不需要维护多套索引同步链路
- 与 Java、Spring Boot、JDBC / MyBatis 集成成熟，适合毕业设计快速落地

缺点：

- 全文检索能力、相关性调优和聚合分析能力不如 Elasticsearch 丰富
- 在超大规模文档或高并发检索场景下，上限不如专用检索系统明显

适用判断：

最适合当前项目，尤其适合作为“业务数据 + 全文检索 + 向量检索”单库方案。

### 5.2 Elasticsearch

优点：

- 同时支持全文检索与向量检索
- 适合做关键词召回、混合检索、过滤查询
- Java 生态集成成熟，资料多，工程落地较方便
- 后续扩展高亮、聚合统计、热点分析也比较顺手

缺点：

- 部署和资源占用高于纯数据库方案
- 向量检索能力虽够用，但不是最专注向量场景的产品

适用判断：

非常适合本项目，尤其适合作为“关键词检索 + 向量检索 + 数据分析”一体化方案。

### 5.3 Milvus

优点：

- 专注向量检索，语义召回能力强
- 适合大规模向量数据与 ANN 检索场景

缺点：

- 需要额外维护全文检索系统
- 对毕业设计来说部署和联调成本偏高
- 如果只是中小规模文档知识库，能力可能超出当前需求

适用判断：

适合对向量检索性能要求较高的项目，但不是当前项目的优先方案。

### 5.4 Qdrant

优点：

- 向量检索能力较强，接口清晰，部署相对 Milvus 更轻量
- 支持元数据过滤，适合知识片段检索场景

缺点：

- 仍然需要搭配其他全文检索方案
- Java 场景下的工程资料和案例相对 Elasticsearch 少一些

适用判断：

可作为 Milvus 的轻量替代，但整体仍属于“向量库 + 其他检索系统”的双系统方案。

## 6. 本项目推荐方案

推荐方案：

- PostgreSQL：保存文档、分片、会话、反馈、配置等业务数据，同时承担全文检索和部分统计能力
- pgvector：负责分片向量存储与相似度检索
- Embedding 模型：负责将知识片段和用户问题转换为向量

推荐原因：

1. 一套 PostgreSQL 同时覆盖业务数据、关键词检索和向量检索，系统结构更清晰。
2. 不需要维护 MySQL 与 Elasticsearch 的双写或同步链路，开发与部署成本更低。
3. 与 Java 和 Spring Boot 集成较成熟，后续实现成本较可控。
4. 更符合毕业设计项目“能讲清楚架构、能完成演示、能逐步扩展”的要求。

## 7. 建议的检索架构

```text
用户问题
    -> 查询预处理
    -> 关键词检索（PostgreSQL Full Text Search）
    -> 向量检索（pgvector Cosine / Inner Product）
    -> 结果合并
    -> 重排
    -> TopN 知识片段
    -> RAG 提示词拼接
    -> 大模型生成答案
```

## 8. 数据落地建议

### 8.1 PostgreSQL 存储内容

- 文档基础信息
- 文档分片元数据与正文内容
- 分片向量
- 全文检索字段与相关索引
- 会话记录
- 问答记录
- 用户反馈
- 系统配置

## 9. 分阶段实施建议

### 第一阶段

- 只接入 PostgreSQL
- 完成文档上传、解析、切片、入库
- 实现基础全文检索
- 完成基础问答页面和后端接口

### 第二阶段

- 接入 Embedding 模型
- 引入 pgvector 向量检索
- 打通语义召回与混合检索链路

### 第三阶段

- 增加检索重排
- 增加检索效果评估指标
- 结合用户反馈持续优化召回质量，必要时评估是否补充独立检索引擎

## 10. 当前项目结论

对于 JavaKQA 项目：

- 从系统设计角度，建议保留向量数据库或向量检索能力
- 从开发节奏角度，第一版可以直接采用 PostgreSQL + pgvector，无需同时引入 MySQL 和 Elasticsearch
- 从毕业设计实现角度，当前推荐采用 PostgreSQL 单库优先方案，后续再按需评估是否拆分检索系统

这样既能保证项目前期快速推进，也能在后期逐步增强 RAG 检索架构设计。
