# 智能问答助手模块开发文档

## 1. 模块定位

智能问答助手模块是 JavaKQA 的核心业务模块，负责承接“用户提问 -> 检索上下文 -> 生成答案 -> 返回引用 -> 保存会话”的完整主链路。

这一模块的目标不是做后台配置，也不是做前台页面容器，而是专门负责问答能力本身。后续真正落代码时，必须保持它作为独立模块存在，不能再混进 system-config 或 user-portal 中。

建议模块名直接使用 intelligent-qa。

## 2. 为什么必须独立成模块

将智能问答助手单独拆成模块，主要是为了保证职责边界稳定。

1. user-portal 只负责用户界面、页面交互和会话展示，不负责问答编排逻辑。
2. system-config 只负责模型参数、检索参数、提示词模板和开关配置，不直接承接问答请求。
3. intelligent-qa 只负责问答业务链路，包括会话管理、检索编排、答案生成和引用组织。
4. framework 只放通用对象、公共枚举、统一返回结构等可复用基础代码。

如果后续继续把问答接口写在 system-config 内，后台模块会越来越重，前台和问答服务的演进节奏也会被绑死，不利于后续替换真实前端工程或独立部署问答服务。

## 3. 当前阶段最主要的功能

当前系统最主要的功能，应明确为智能问答助手本身，而不是外围管理能力。

围绕这个核心，第一优先级只抓住以下能力：

1. 用户发起新对话。
2. 用户在已有会话中连续追问。
3. 系统基于知识库检索相关内容。
4. 系统生成结构清晰、可引用来源的答案。
5. 系统在左侧展示历史对话列表，支持切换查看。
6. 系统保存每轮消息，形成完整会话上下文。

像用户管理、复杂配置编排、运维统计、批量反馈分析，都不是这个模块第一版最核心的交付重点。

## 4. 模块职责边界

### 4.1 intelligent-qa 负责的内容

- 问答会话创建、查询、删除、重命名
- 消息发送、消息保存、消息上下文拼接
- 查询改写、检索召回、候选片段排序
- 提示词组装、模型调用、答案生成
- 引用来源组织、下一步建议生成
- 问答耗时、状态、异常原因记录

### 4.2 intelligent-qa 不负责的内容

- 后台配置表维护
- 模型密钥录入页面
- 普通用户登录页和门户页展示
- 后台管理员权限页面
- 知识库文档导入的后台管理页面

### 4.3 与其他模块的协作关系

- user-portal 调用 intelligent-qa 暴露的问答接口，负责前台页面交互。
- system-config 维护问答运行配置，intelligent-qa 只读取生效配置，不承担后台管理职责。
- framework 提供公共基础对象，避免三个模块重复定义通用结构。

## 5. 第一版功能范围

第一版只建议实现能直接体现“智能问答助手”价值的核心闭环。

### 5.1 会话能力

- 新建对话
- 会话列表查询
- 按最近活跃时间排序
- 切换会话查看历史消息
- 删除会话
- 自动生成会话标题

### 5.2 问答能力

- 输入问题并发送
- 支持连续追问
- 返回答案正文
- 返回答案引用来源
- 返回命中知识片段摘要
- 返回建议追问问题

### 5.3 上下文能力

- 保存每轮用户消息和助手消息
- 控制上下文窗口长度
- 支持基于最近若干轮消息做上下文增强
- 当上下文过长时做摘要压缩或裁剪

### 5.4 异常兜底能力

- 检索为空时给出明确提示
- 模型调用失败时返回友好提示
- 超时、限流、配置缺失时返回可识别状态码和错误信息
- 页面上明确展示“正在生成中”“生成失败”“已完成”三类状态

## 6. 问答界面设计要求

问答界面应参考当前主流浏览器中的问答产品，但不做复杂装饰，整体方向必须是简洁、聚焦、低干扰。

核心要求如下：

1. 对话列表放在左侧侧边栏。
2. 右侧为当前会话消息流和输入区。
3. 页面视觉尽量轻，减少大面积卡片堆叠。
4. 输入框固定在底部，支持多行输入。
5. 答案中的引用来源要能明显区分，但不要抢主内容视觉。
6. 手机端侧边栏改为可收起抽屉，不要强行并排展示。

### 6.1 页面布局建议

```text
+--------------------------------------------------------------+
| 左侧侧边栏                     | 右侧主对话区                 |
|--------------------------------|------------------------------|
| 新建对话按钮                   | 当前会话标题                 |
| 搜索会话                       | 模型状态 / 响应状态          |
|                                |------------------------------|
| 今天                            | 用户问题                     |
| - Spring Boot 自动配置原理      | 助手回答                     |
| - MyBatis 缓存机制              | 引用来源                     |
|                                | 建议追问                     |
| 昨天                            |------------------------------|
| - Redis 哨兵与集群差异          | 底部输入框 + 发送按钮        |
+--------------------------------------------------------------+
```

### 6.2 左侧侧边栏建议

- 顶部放“新建对话”按钮
- 下方放会话搜索框
- 会话列表按“今天、近 7 天、更早”分组
- 每个会话项展示标题、最后一条摘要、最近更新时间
- 鼠标悬停时显示重命名、删除入口
- 当前选中的会话高亮

### 6.3 主对话区建议

- 顶部只保留当前会话标题和简要运行状态
- 中间区域展示用户消息和助手消息流
- 助手回答优先展示正文，再展示引用与追问建议
- 底部固定输入区，支持 Enter 发送、Shift+Enter 换行
- 生成过程中允许“停止生成”或至少展示处理中状态

### 6.4 视觉风格建议

- 颜色保持克制，避免过多强对比色块
- 主对话区背景尽量干净，突出文字可读性
- 侧边栏宽度固定，避免频繁跳动
- 文本字号层级清晰，答案正文优先级最高

## 7. 核心业务流程

### 7.1 单轮问答流程

1. 用户在前台输入问题。
2. user-portal 将问题提交给 intelligent-qa。
3. intelligent-qa 读取当前生效配置。
4. intelligent-qa 对问题做预处理与必要的查询改写。
5. 检索层召回候选知识片段。
6. 对候选结果进行去重、排序与截断。
7. 将高相关片段拼接进提示词上下文。
8. 调用大模型生成答案。
9. 保存问题、答案、引用来源和耗时。
10. 返回答案正文、引用来源、会话信息和建议追问。

### 7.2 多轮问答流程

1. 用户进入已有会话继续追问。
2. intelligent-qa 读取最近若干轮消息。
3. 对当前问题做上下文补全。
4. 重新执行检索与生成。
5. 保存本轮消息并刷新会话最近活跃时间。

## 8. 接口规划建议

接口前缀建议统一使用 /api/assistant。

### 8.1 会话接口

- POST /api/assistant/conversations：新建会话
- GET /api/assistant/conversations：查询会话列表
- GET /api/assistant/conversations/{conversationId}/messages：查询会话消息
- PUT /api/assistant/conversations/{conversationId}/title：修改会话标题
- DELETE /api/assistant/conversations/{conversationId}：删除会话

### 8.2 问答接口

- POST /api/assistant/chat：发送问题并返回答案
- POST /api/assistant/chat/continue：基于已有会话继续追问
- POST /api/assistant/messages/{messageId}/regenerate：重新生成回答

### 8.3 运行信息接口

- GET /api/assistant/runtime-config：读取当前生效的只读运行参数快照
- GET /api/assistant/health：问答模块健康检查

## 11. 代码结构建议

真正落地实现时，建议 intelligent-qa 模块内部至少按以下结构拆分：

```text
intelligent-qa
  └── src/main/java/com/qingyun/intelligentqa
      ├── api
      ├── controller
      ├── service
      ├── domain
      ├── repository
      ├── retrieval
      ├── llm
      ├── config
      └── support
```

各层职责建议如下：

- controller：接收前台请求，做参数校验和结果返回
- service：编排问答主流程
- retrieval：封装关键词检索、向量检索、重排逻辑
- llm：封装模型调用、提示词组装、流式或非流式返回
- repository：会话、消息、引用等持久化
- domain：核心业务对象和规则
- support：异常、工具类、状态枚举、转换器

## 12. 与现有工程的落地关系

按当前仓库结构，后续实现时应遵守以下原则：

1. 在父工程 pom 中将 intelligent-qa 作为独立模块接入。
2. user-portal 仅调用 intelligent-qa 的接口，不直接拼接问答业务逻辑。
3. system-config 仅负责维护配置，不再直接对外承接问答 API。
4. 如果确实存在三个模块都要复用的对象，再下沉到 framework，而不是反向耦合到 intelligent-qa。

## 13. 第一版开发顺序建议

### 第一阶段

1. 建立 intelligent-qa 独立 Maven 模块。
2. 完成会话表、消息表、引用表设计。
3. 先打通会话列表、消息保存、占位问答接口。
4. 前台页面先落“左侧会话列表 + 右侧对话区”的基础形态。

### 第二阶段

1. 接入真实检索链路。
2. 接入模型调用。
3. 返回引用来源和建议追问。
4. 补齐多轮上下文能力。

### 第三阶段

1. 增加会话搜索、重命名、删除。
2. 优化流式响应体验。
3. 增加失败重试、重新生成和答案反馈。
4. 做性能监控与耗时统计。

## 14. 当前文档结论

当前阶段应先把“智能问答助手”确认为系统主功能，并围绕它做独立模块设计。

最重要的落地约束有两条：

1. 问答业务代码必须拆到 intelligent-qa 模块，不再混入 system-config 或 user-portal。
2. 问答页面必须走简洁路线，左侧放对话列表，右侧聚焦当前会话和输入区。

在这两个前提稳定之后，再继续推进检索、模型、引用来源和多轮对话等具体实现，整体系统才不会再次出现职责混杂的问题。
